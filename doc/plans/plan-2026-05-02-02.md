# Plan 2026-05-02-02 — Facade namespace

## Goal

Add an `agogo` facade crate so downstream users and CLI code can refer
to project modules through `agogo::{core,host}` instead of fused crate
roots like `agogo_core` and `agogo_host_link`.

## Dependency Graph

```
T1 facade crate + feature gates
    |
    v
T2 CLI import migration
    |
    v
T3 docs and verification
```

## Tasks

### T1 — Facade crate + feature gates

**Problem.** Cargo package names are flat, so the workspace exposes
`agogo-core`, `agogo-host`, `agogo-host-cpal`,
`agogo-host-link`, and `agogo-host-midi` as separate fused Rust crate
roots.

**Solution.** Add a workspace member package named `agogo` whose
library re-exports the stable internal crates as nested modules:
`agogo::core`, `agogo::host`, `agogo::host::cpal`,
`agogo::host::link`, and `agogo::host::midi`. Keep the backend crates
optional and feature-gated so the default workspace build does not pull
platform or Link dependencies.

### T2 — CLI import migration

**Problem.** The CLI is the main in-repo consumer of fused roots, which
makes the intended public namespace hard to see in day-to-day code.

**Solution.** Point `agogo-cli` at the facade crate and replace CLI
imports/usages with the nested namespace. Do not change the lower-level
host backend crates to depend on the facade, because that would create
cycles; backend crates use private namespace shims for their
`agogo::core::*` imports.

### T3 — Docs and verification

**Problem.** A namespace refactor can compile locally while docs and
smoke coverage still advertise the old public shape.

**Solution.** Add compile-time namespace smoke tests in the facade crate
and update nearby comments that mention the fused roots as the preferred
surface. Preserve historical plan/review text unless it is actively
misleading in touched files.
