# Plan 2026-05-04-03 - Chan facade, rate names, and deterministic render

## Goal

First make a few mechanical naming/module moves so the public API reads like
the current crate boundary, then add a hardware-free render path that exercises
the real scheduling/rendering pipeline and produces deterministic output for
README demos, CI, and property tests.

The mechanical preface is intentionally behavior-preserving:

- expose the pure channel crate as `agogo::chan` and migrate downstream imports
  away from `agogo::core` for channel/timing/sink/control types;
- merge `conn/boundary.rs` into `conn/float.rs` so f64 boundary helpers live
  next to the f64 Conn ladder;
- move `conn/sample.rs` to `conn/rate.rs`;
- rename sample-rate marker types from `S044` / `S048` / ... to
  `R044` / `R048` / ...;
- rename all sample-rate connection constants the same way, e.g.
  `S176Q016` becomes `R176Q016` and `FD12S048` becomes `FD12R048`.

The first slice is intentionally internal-source only. External audio input,
Ableton Link, native timestamped MIDI, device timing, and real cpal/midir hosts
stay out of scope.

## Context

The current public demo path is `agogo run`, which is useful but hardware
dependent: it opens cpal and optionally midir, then runs until Ctrl-C. A public
GitHub README needs a command that works on a fresh checkout and CI runner
without audio or MIDI devices.

The same deterministic harness can carry the property-testing idea from
`doc/notes/prop-tests.md`: generate channel specs/configs, run multiple buffer
epochs, and assert pipeline invariants. The exact cancellation property with
opposite polarity should wait until CV/audio output has an explicit signed
polarity model. Today `AudioIo` is mono, `AudioRole` only has `Click`,
`CvRole` is a stub family, and the audio click renderer writes/clamps `f32`
PCM directly.

## Proposed CLI

Add a command shaped like:

```bash
cargo run -p agogo-cli --features run --bin agogo -- render \
  --source internal \
  --bpm 120 \
  --sr 48000 \
  --duration-bars 1 \
  --ch 'id=three,dev=midi,mode=click,grid=t2t,out=diag' \
  --ch 'id=two,dev=midi,mode=click,grid=t2,out=diag'
```

The command should print deterministic JSON by default. A later plan can add a
pretty table, CSV, or MIDI-file output if useful.

Example shape:

```json
{
  "sample_rate": 48000,
  "bpm": "120",
  "duration": {"bars": 1},
  "channels": [
    {"id": "three", "events": 3},
    {"id": "two", "events": 2}
  ],
  "midi": [
    {"sample": 0, "channel": "three", "bytes": [250]},
    {"sample": 0, "channel": "three", "bytes": [153, 76, 100]}
  ],
  "dropped": 0
}
```

Exact schema can change during implementation, but it must stay stable enough
for README examples and snapshot-style tests.

## Tasks

### T1 - Add the `agogo::chan` facade and migrate imports

In `crates/agogo`, add a `chan` module facade that re-exports the public surface
of `agogo-chan`. Keep `agogo::core` for runtime orchestration only.

Then update workspace users:

- CLI and host crates import channel/timing/sink/control/conn types through
  `agogo::chan`;
- runtime orchestration types stay under `agogo::core`;
- rustdoc links and public docs stop describing pure channel types as
  `agogo::core::*`;
- temporary compatibility re-exports are allowed only if the migration would
  otherwise make the sprint too large, and must be listed in Review with a
  removal plan.

Verification should include a targeted search for remaining `agogo::core::`
uses that name `channel`, `conn`, `control`, `sink`, `test`, or `time`.

### T2 - Merge `conn::boundary` into `conn::float`

Move the f64 boundary helpers from `crates/chan/src/conn/boundary.rs` into
`crates/chan/src/conn/float.rs`.

Required shape:

- `f64_bpm_to_tempo`, `f64_phase_to_phase`, `tempo_to_f64_bpm`,
  `tempo_to_hz`, `pico_to_f64_seconds`, `pico_to_samples`, and related tests
  live in `conn::float`;
- production callers use `conn::float::*`;
- `conn.rs` no longer declares `pub mod boundary`;
- `scripts/check-floats.sh` allowlist and AGENTS prose are updated for the
  moved code;
- if a compatibility `conn::boundary` shim is kept, it must be deprecated,
  covered by a Review note, and removed in the same PR unless there is a
  concrete external-breakage reason.

### T3 - Rename `conn::sample` to `conn::rate`

Move `crates/chan/src/conn/sample.rs` to `crates/chan/src/conn/rate.rs` and
update module declarations, imports, docs, and allowlists.

The module owns sample-rate-indexed Conn types, but the public vocabulary should
be "rate" because the markers are not sample values.

### T4 - Rename rate markers and rate connections

Rename all sample-rate markers from `SXYZ` to `RXYZ`:

- `S044`, `S048`, `S088`, `S096`, `S176`, `S192`
- comments, macro invocations, tests, and generated helper names where the
  helper exists only to name a rate arm.

Rename all sample-rate connection constants/types consistently:

- `S048I064` -> `R048I064`
- `S048Q016` -> `R048Q016`
- `S048S044` -> `R048R044`
- `FD12S048` -> `FD12R048`
- same shape for every supported rate, including examples such as
  `S176Q016` -> `R176Q016`.

Avoid broad compatibility aliases unless necessary. If aliases are retained,
mark them deprecated and list every alias in Review with a removal plan.

### T5 - Add a core deterministic render harness

Create a pure helper that advances `Playhead::<Rate>` over a caller-selected
number of buffers without opening cpal or midir.

The helper should:

- use the same `Playhead::on_buffer` path as `agogo run`;
- use empty input and fixed output buffers through `AudioIo`;
- use `TestSink` / `DiagnosticSink` or a small structured capture sink;
- preserve `at_sample` values and MIDI bytes;
- report per-channel counts if channel attribution can be carried without
  widening hot-path complexity.

Prefer placing reusable logic in `agogo-core`; keep CLI JSON formatting in
`agogo-cli`.

### T6 - Add `agogo render`

Add a CLI command under the existing command module layout.

Inputs:

- `--source internal` only for this plan;
- `--bpm`, `--sr`, `--buffer-frames`, and repeatable `--ch` using the same
  parse/validation rules as `run`;
- one bounded duration control, preferably `--duration-bars` for musical README
  demos and `--duration-ms` only if needed for test ergonomics.

Errors should be precise and boundary-level:

- reject non-internal source;
- reject unsupported sample rates before rendering;
- reject real output targets that do not make sense in diagnostic mode if `out`
  semantics are not reused.

### T7 - JSON output contract

Define a small serde-serializable report type.

At minimum include:

- sample rate, BPM, duration, buffer size;
- ordered MIDI records with sample index and bytes;
- output timing capability as diagnostic/best-effort metadata;
- dropped/overflow count, expected to be zero;
- channel summary if available.

Avoid promising physical timing. This is an offline render report, not proof a
hardware backend honors `at_sample`.

### T8 - Property: deterministic render identity

Generate supported channel specs/configs and assert two independent render runs
produce identical reports across multiple buffers.

The generator should cover meaningful scheduling domains without bounding away
interesting cases:

- supported sample rates;
- buffer sizes that cross event boundaries;
- grids, swing, delay, offset, bars;
- MIDI clock and MIDI click roles currently implemented.

If a domain must be bounded, document why immediately above the strategy and add
a boundary spot-check.

### T9 - Property: equivalent channel scheduling identity

Generate two channels with the same scheduling config and assert their scheduled
event timelines are identical across a multi-buffer run.

This is the current safe subset of the future polarity-cancellation idea: it
checks parser/validation/scheduler/buffer-boundary behavior without inventing a
polarity model.

### T10 - Track the future cancellation property

Record the deferred cancellation property in this plan's Review or Deferred
section and, if useful, in `doc/todo.md`:

> Once CV/audio output has explicit signed polarity and a non-clipping
> accumulator, two identical channels with opposite polarity render to silence
> across any buffer epoch sequence.

Do not add test-only polarity fields to production types just to force this
property now.

### T11 - README integration

After Plan 2026-05-04-02 rewrites the README, add the render command as the
primary hardware-free quickstart. The README should distinguish this deterministic
offline report from `agogo run`, which opens real devices.

## Deferred

- External source render mode. It needs deterministic synthetic input pulses and
  PLL expectations, not real cpal input.
- Link render mode. It needs a fake Link host-time/session model.
- Native timestamped MIDI backends and hardware timing validation.
- Pretty/text/CSV/MIDI-file output formats.
- Opposite-polarity cancellation property. This should land with explicit
  signed CV/audio output and a non-clipping accumulator.
- External compatibility for old `agogo::core` pure-type paths, `conn::sample`,
  and `SXYZ` rate names. This plan prefers a clean mechanical rename while the
  project is still pre-release and `publish = false`.
