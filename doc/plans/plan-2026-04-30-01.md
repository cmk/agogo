# Plan 2026-04-30-01 — stdio-core control adapter

## Goal

Land agogo's v0.3 stdio-core control seam: add an `agogo-stdio`
adapter crate that implements stdio-core's `StudioMcpServer`, mounts
cleanly, and routes async tool calls into agogo's RT-safe control
bridge without depending on observation.

## Dependency Graph

```
T1 stdio crate skeleton + path dependency
    |
    v
T2 RT-safe control bridge
    |
    v
T3 StudioMcpServer lifecycle + tool routing
    |

    |

```

## Tasks

### T1 — `crates/stdio` workspace member

**Problem.** agogo currently has no stdio-core-facing crate, so the
v0.3 roadmap is still a design dependency rather than a buildable
adapter.

**Solution.** Add `crates/stdio` as package `agogo-stdio`, behind a
path dependency on `../stdio-core/stdio-core` until stdio-core 0.2 is
published. Keep the crate separate from `agogo-core` so the RT core
does not depend on stdio-core.

Public surface:

```rust
pub struct AgogoDriver;
pub struct AgogoDriverConfig;
```

### T2 — RT-safe control bridge

**Problem.** stdio-core dispatch is async and may backpressure, while
agogo's audio callback must never await, allocate, or route control
through dropping observation channels.

**Solution.** Add an adapter-owned bridge with two write paths:

- atomics for last-value controls such as tempo;
- `rtrb` SPSC commands for ordered operations such as channel
  reconfigure, start, stop, and locate.

`handle_call` returns after the bridge accepts the write. If the SPSC
is full, return a tool error instead of silently dropping the command.

### T3 — `StudioMcpServer` implementation

**Problem.** stdio-core Plan 10 adds lifecycle hooks that agogo must
use to mount resources and release them predictably.

**Solution.** Implement `StudioMcpServer` for `AgogoDriver`:

- tools: `agogo.tempo.set`, `agogo.channel.configure`,
  `agogo.start`, `agogo.stop`, `agogo.locate`;
- `on_mount(bus)` stores the bus handle for async-side semantic
  events only and marks the driver online;
- `on_unmount()` stops adapter background tasks, drops bridge handles,
  and is idempotent;
- no callback-side code calls stdio-core or touches the bus.

Tool success returns JSON shaped like:

```json
{ "accepted": true, "applies_by": "next_buffer" }
```

### T4 — inverse ops and dispatcher tests

**Problem.** stdio-core persistence and future undo need semantic
inverse declarations, but emitted audio or MIDI cannot be undone.

**Solution.** Implement `inverse_op` for invertible future-state
controls only. Tempo restores the captured prior tempo; transport
commands invert only when a prior semantic transport position is
available. Tests use stdio-core's dispatcher with a mock machine and
no observation subscriber.

### T5 — documentation alignment

**Problem.** The version roadmap must point at the concrete
stdio-core integration contract so future v0.3 work does not infer
behavior from stale trait sketches.

**Solution.** Keep `doc/versions/version-0.3.md` aligned with
`../stdio-core/doc/designs/agogo.md` and stdio-core Plan 10. Do not
add absolute local paths or user-home paths.

## Verification

### Properties (must pass)

| Property | Module | Invariant |
|----------|--------|-----------|
| `tempo_set_has_no_rt_alloc` | `agogo_stdio::rt_bridge` | `agogo.tempo.set { bpm }` produces zero allocations on the audio-thread bridge path. |
| `tempo_set_applies_within_one_buffer` | `agogo_stdio::rt_bridge` | A tempo write accepted by the bridge is visible to the callback by the next buffer. |
| `tick_stream_never_drops_under_command_load` | `agogo_stdio::rt_bridge` | Generated command sequences at sustained load do not drop tick output from the running mock machine. |
| `agogo_control_never_routes_through_observation` | `agogo_stdio::tools` | Tool dispatch succeeds without an `ObservationDispatcher` subscriber or stream. |
| `agogo_mount_unmount_idempotent` | `agogo_stdio::driver` | Repeated mount/unmount leaves the driver offline and releases each background handle once. |
| `inverse_op_is_round_trip` | `agogo_stdio::tools` | Invertible tools return the semantic machine snapshot to its prior state. |

### Spot checks

| Test | Assertion |
|------|-----------|
| `driver_advertises_initial_tool_set` | `tool_names()` contains the five v0.3 tools exactly once. |
| `queue_full_returns_tool_error` | A full ordered-command queue returns an error instead of dropping the command. |
| `tempo_set_response_names_next_buffer` | Successful tempo writes return `{ "accepted": true, "applies_by": "next_buffer" }`. |
| `unmounted_driver_rejects_calls` | Calls before successful mount fail in the adapter rather than touching the bridge. |

- Audio-rate event logging: out of scope; use future agogo trace
  tooling if continuous tick/CV/MTC recording is needed.

## Review

- **Design deviation:** T1/T3 landed as a buildable agogo-owned
  `agogo-stdio` crate with a driver-shaped API, but not yet a direct
  `stdio_core::driver::StudioMcpServer` impl. The sibling stdio-core
  checkout pins Rust 1.92 while agogo is pinned to Rust 1.85; adding a
  direct stdio-core path dependency to this workspace would break
  `cargo test --workspace`. The trait impl resumes once the upstream
  dependency is published with compatible MSRV policy or agogo's MSRV
  intentionally moves.
