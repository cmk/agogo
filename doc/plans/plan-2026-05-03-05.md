# Plan 2026-05-03-05 - Two-repo agogo / stdio-core steel thread

## Goal

Define the next integration slice between agogo and stdio-core. This is a
planning artifact first: agogo gets an implementation plan for its side of the
steel thread, and stdio-core gets a companion plan shape to copy into
`stdio-core/doc/plans` after the current stdio-core WIP branch lands.

The immediate steel thread is two repositories, not three. The `stdio` repo can
remain the later community-facing client harness; the hard boundary to prove now
is `stdio-core <-> agogo`.

## Steel Thread

Exercise this exact path:

```text
stdio-core dispatcher + InMemoryLog
  -> stdio-core McpServer wrapper around agogo-host
  -> agogo AgogoDriver::handle_call
  -> agogo ControlProducer admission
  -> agogo apply_control_to_playhead
  -> agogo SnapshotSlot / SnapshotPublisher
  -> stdio-core ObservationParams + Event::ToolObservation
  -> stdio-core InterfaceSnapshot + BeliefState replay
```

Commands in scope:

- `agogo.tempo.set { bpm, source_id, command_id?, time_domain: "rt_buffer",
  deadline_buffer? }`
- `agogo.start { source_id, command_id?, time_domain: "rt_buffer",
  deadline_buffer? }`

The thread proves:

- the driver mounts and exposes metadata plus an `agogo-state` surface manifest;
- command lifecycle facts are logged through stdio-core's lossless dispatcher
  path;
- agogo admission responses include status, command id, source id, time domain,
  and deadline;
- accepted commands apply through `Playhead` by the declared RT-buffer deadline;
- `agogo-state` reports the resulting tempo or transport state;
- stdio-core projects the observation into `InterfaceSnapshot`;
- control works with zero observation subscribers;
- replay of the fixture log reconstructs the same command and belief facts.

## Agogo-Side Plan

### T1 - Rust toolchain parity with stdio-core

Problem or motivation: agogo started this branch pinned to Rust 1.85 while
stdio-core pins Rust 1.92. The immediate integration slice is easier to
validate and maintain when both repositories build against the same compiler,
and the current dependency-boundary note should stop depending on a toolchain
mismatch.

Solution: bump agogo's Rust pin to stdio-core's Rust 1.92 across:

- workspace `rust-version` in `Cargo.toml`;
- `rust-toolchain.toml`;
- CI workflow Rust toolchain actions in `.github/workflows/`;
- any docs or comments that still describe Rust 1.85 as the active pin.

Keep the bump mechanical and separate from runtime behavior changes.

### T2 - Runtime helper

Problem or motivation: `agogo-host` has the pieces of the steel thread
(`AgogoDriver`, `ControlConsumer`, `apply_control_to_playhead`,
`SnapshotSlot`, and `SnapshotPublisher`) but no single test/runtime helper that
stdio-core can wrap without knowing agogo internals.

Solution: add a small `agogo_host::runtime` helper that owns:

- `AgogoDriver`;
- `ControlConsumer`;
- `Playhead`;
- `SnapshotSlot` writer/reader;
- `SnapshotPublisher`.

Expose methods shaped for tests and the future adapter wrapper:

- `mount()`;
- `unmount()`;
- `handle_call(tool, args)`;
- `advance_buffer()`;
- `publish_snapshot(sink)`.

The helper must stay stdio-core-free. Dependency direction for the integration
harness should be stdio-core test/dev code depending on agogo, not agogo
importing stdio-core.

### T3 - Structured runtime report

Problem or motivation: stdio-core needs to assert the full sequence without
parsing logs or snapshots ad hoc.

Solution: have the helper expose a compact step report containing:

- admission JSON from `AgogoDriver::handle_call`;
- `CommandApplyReport`;
- current snapshot sequence;
- optional observation params emitted by `SnapshotPublisher`.

The report is for tests and integration harnesses; it must not add work to the
RT callback path.

### T4 - Metadata and surface helper

Problem or motivation: stdio-core already has `ToolMetadata` and
`DriverSurfaceManifest`; agogo should provide equivalent agogo-owned facts
without importing those types.

Solution: add agogo-native helper data for:

- tool timing and safety intent for `agogo.tempo.set`, `agogo.start`,
  `agogo.stop`, `agogo.locate`, and `agogo.channel.configure`;
- `agogo-state` surface declaration with `stream_id = "agogo.main"` and
  `form_id = "agogo.main"`;
- observation subscription for `agogo.main`.

stdio-core's companion wrapper maps these facts into stdio-core types.

### T5 - Agogo verification

Add focused tests proving:

- `runtime_tempo_set_applies_and_snapshots`;
- `runtime_start_applies_and_snapshots`;
- `runtime_control_without_observation_sink`;
- `runtime_metadata_matches_stdio_core_contract`.

Run the normal agogo gates:

- `cargo fmt --all -- --check`;
- `scripts/check-pii.sh`;
- `scripts/check-floats.sh`;
- `scripts/check-layers.sh`;
- `scripts/check-connections.sh`;
- `scripts/check-boundary-panics.sh`;
- `cargo test --workspace --quiet`;
- `cargo clippy --all-targets --quiet -- -D warnings`;
- `git diff --check`.

## stdio-core Companion Plan

Copy this section into the next stdio-core plan after the current stdio-core WIP
branch lands.

### Goal

Replace stdio-core's scripted agogo fixture with a wrapper over the real
agogo-host runtime helper, while keeping `stdio` out of the critical path
for this sprint.

### T1 - Roadmap wording

Update `doc/versions/version-0.2.md` so the immediate property is the two-repo
agogo/std-core thread. Defer the `stdio` repo soft-driver harness as the later
community-client S6 follow-up.

Suggested property rename:

- `three_repo_steel_thread` -> `two_repo_agogo_runtime`

### T2 - Dev-only agogo dependency

Add a test/dev path dependency or feature-gated fixture path to
`../agogo/crates/host`. Keep it out of stdio-core's production runtime surface
unless the compatibility story is explicit.

### T3 - `AgogoHostMcpServer`

Implement a stdio-core testkit wrapper that:

- owns the agogo runtime helper;
- implements `stdio_core::driver::McpServer`;
- maps agogo metadata into `ToolMetadata`;
- maps agogo surface declarations into `DriverSurfaceManifest`;
- translates agogo `push::ObservationParams` into stdio-core
  `ObservationParams`;
- keeps control independent of observation subscribers.

### T4 - Dispatcher/log/interface integration tests

Add integration tests that spawn stdio-core's dispatcher with `InMemoryLog`,
register `AgogoHostMcpServer`, dispatch the scoped commands, advance agogo, and
publish observations.

Required tests:

- `two_repo_tempo_set_logs_accept_apply_observe`;
- `two_repo_start_logs_accept_apply_observe`;
- `agogo_control_without_observation_subscriber_real_adapter`;
- `agogo_surface_projects_into_interface_snapshot`;
- `agogo_runtime_log_replays`;
- `stdio_repo_not_required_for_agogo_runtime`.

The log replay assertion should prove command lifecycle determinism and preserve
the existing rule that a command-only response does not become observed hardware
truth without an observation fact.

## Deferred

- Direct `stdio` repo integration and soft-driver harness.
- Rich TUI rendering beyond the existing `InterfaceSnapshot` projection.
- Native timestamped MIDI backends.
- Full v0.3 Link/MIDI-clock follower work.
