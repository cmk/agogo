# Plan 2026-05-04-04 - CV pulse MVP for public demos

## Goal

Fill the largest user-visible output gap that is still MVP-sized before opening
the repository: make `CvRole::Pulse` real enough to run, test, and document.

The previous plan already landed the requested mechanical preface:

- `agogo::chan` facade in the public `agogo` crate;
- `conn::sample` renamed to `conn::rate`;
- rate markers and rate Conns renamed from `SXYZ` to `RXYZ`;
- f64 boundary helpers moved out of the old `conn::boundary` public module.

This plan builds on that shape. GitHub open-sourcing remains separate from
crates.io publishing: keep `publish = false`, do not add registry metadata, and
do not treat `cargo package` / `cargo publish --dry-run` as acceptance gates.

## Context

The README now has a hardware-free `agogo render` path and honest status text,
but it still has to say CV pulse/LFO roles are stubs. That is a conspicuous gap
for a timing/sync engine whose value proposition includes driving modular or
analog clock inputs.

`doc/designs/cv-pulse.md` already chooses a narrow shape:

- single-sample impulse as the baseline pulse;
- optional bipolar reset to avoid DC creep on AC-coupled interfaces;
- explicit handling when the reset spills across a buffer boundary;
- no limiter or master processing on the sync bus.

This plan implements only pulse output. LFO, multi-channel hardware routing,
latency calibration, and heterogeneous output dispatch stay with the later
v0.4 roadmap.

## Proposed CLI

Offline deterministic demo:

```bash
cargo run -p agogo-cli --bin agogo -- render \
  --source internal \
  --bpm 120 \
  --sr 48000 \
  --duration-bars 1 \
  --ch 'id=cv,dev=cv,mode=pulse,grid=t4,out=diag'
```

Hardware-backed smoke path:

```bash
cargo run -p agogo-cli --features run --bin agogo -- run \
  --source internal \
  --bpm 120 \
  --sr 48000 \
  --ch 'id=cv,dev=cv,mode=pulse,grid=t4,out=default'
```

The hardware-backed command should be documented as a raw sync output path:
route it only to an interface output intended for clock/CV, not speakers or a
processed monitor bus.

## Tasks

### T1 - Parse and validate `dev=cv,mode=pulse`

Extend the channel spec parser so `dev=cv` is accepted with `mode=pulse`.

Required shape:

- default `mode` for `dev=cv` is `pulse`;
- `dev=cv,mode=lfo` parses only if the current code can reject it with a clear
  "unsupported in this plan" error before runtime, otherwise keep it a parser
  error;
- `CvRole::Pulse` converts to `Channel::Cv`;
- unknown CV shaping keys are hard errors for now;
- docs and parser help state that CV pulse uses fixed MVP pulse settings.

### T2 - Add pulse shape state

Add the minimal state needed to render a pulse train across buffers.

Required shape:

- one-sample positive impulse;
- optional one-sample negative reset for bipolar mode;
- a pending-reset flag when the reset lands in the next buffer;
- fixed MVP default is bipolar unless the existing design review shows a better
  reason to default monopolar.

Avoid adding user-facing amplitude or width knobs in this plan unless the
implementation needs them internally. The goal is a stable first behavior, not
a calibration surface.

### T3 - Render CV pulse through the existing audio buffer

Wire `Channel::Cv { role: CvRole::Pulse, .. }` into the `Playhead::on_buffer`
path so it writes to `AudioIo::output`.

Required shape:

- scheduling uses the same event timeline as MIDI/audio click channels;
- the output buffer is written deterministically in offline render;
- audio click and CV pulse channels can coexist in the same mono diagnostic
  buffer for this MVP, with CV pulses rendered last and given full-scale
  priority over click samples at pulse/reset overlaps;
- clipping/saturation behavior is explicit and tested.

Do not widen `AudioIo` to interleaved multi-channel output in this plan unless
the existing host API makes the mono MVP impossible. Multi-output routing is a
larger heterogeneous-output sprint.

### T4 - Report CV pulse diagnostics in offline render

Extend `agogo render` output enough to make CV pulse inspectable without
hardware.

At minimum include:

- nonzero audio sample count;
- peak positive and negative sample values or q15 equivalents;
- a per-channel summary if attribution can be carried without widening the hot
  path;
- stable JSON tests for the one-bar pulse demo.

The report must remain an offline diagnostic, not a physical timing claim.

### T5 - Add properties for pulse timing and energy

Add property tests for the CV pulse renderer.

Required properties:

- `cv_impulse_sample_exact`: every scheduled pulse writes the positive impulse
  at the intended sample index;
- `cv_impulse_one_sample_energy`: monopolar pulses produce exactly one non-zero
  sample per event;
- `cv_bipolar_reset_crosses_buffer`: bipolar pulses produce one positive sample
  and one negative reset sample separated by one frame, including when the reset
  spills into the next buffer.

Use meaningful domains for supported sample rates, buffer sizes, grids, bars,
delay, and swing. If a generator must be bounded for runtime, document why and
add explicit boundary spot-checks.

### T6 - Keep parser/render docs current

Update public docs after the implementation lands:

- README Current Status no longer calls `CvRole::Pulse` a stub;
- README shows a hardware-free CV pulse render command;
- hardware-backed docs warn that CV pulse output is a raw sync signal;
- `doc/versions/version-0.4.md` notes that the mono pulse MVP landed ahead of
  full heterogeneous output;
- crates.io publishing remains explicitly deferred.

## Deferred

- `CvRole::Lfo` rendering.
- User-facing pulse width, amplitude, polarity, and calibration controls beyond
  the fixed MVP defaults.
- Interleaved multi-output `AudioIo` and per-channel hardware routing.
- OSC, MTC, DIN, and native timestamped MIDI backends.
- Hardware-in-the-loop validation of interface output voltage or jitter.
- crates.io publishing readiness and package metadata.

## Review

- `crates/chan/src/sink/audio.rs` still says `AudioIo` output is empty until
  v0.4 in several comments, but `agogo render` already writes mono audio click
  diagnostics today. Update those comments while adding CV pulse so the docs do
  not understate the current output path.
- `README.md` currently says "CV pulse/LFO roles are spec stubs, with no CV
  renderer yet." That sentence becomes stale once T3 lands and must be replaced
  in the same implementation branch.
