# Plan 2026-05-06-01 - Interleaved OfflinePcm, WAV render, live multi-channel audit

## Context

Plan 2026-05-05-02 (PR #81, merged) shipped `render_offline_capture`
returning `OfflinePcm { lanes: Vec<Vec<f32>>, ... }` — planar storage
indexed `[lane][sample]`. Two pressures motivate revisiting that shape
in this sprint:

1. **The capture loop is a per-sample push.** For every offline buffer,
   `render_offline_with_rate` runs `frames * output_channels` individual
   `Vec::push` calls to split the renderer's interleaved scratch buffer
   into the per-lane Vecs (`crates/core/src/transport.rs:963-971`). The
   renderer's native layout is interleaved (PCM ABI), and a single
   `extend_from_slice` per buffer would replace ~1.5M push calls (96k
   frames × 16 channels) with one memcpy. The proptest battery's
   per-render capture overhead drops correspondingly.
2. **The deferred WAV-render CLI feature wants interleaved.** `hound`'s
   `WavWriter::write_sample` consumes samples in interleaved order; a
   planar `OfflinePcm` would have to be re-interleaved on the way out,
   throwing away the work the planar split just did. Picking the right
   storage now means WAV is a thin consumer rather than another
   transposition layer.

Two adjacent items from the previous plan's Deferred list ride
naturally on this branch:

- **WAV-render CLI** (`agogo render --wav-out FILE`). With interleaved
  capture in place, this is a small `hound` shim plus argv plumbing.
  Lands the first downstream consumer of `render_offline_capture` and
  validates the storage choice end-to-end.
- **Multi-channel live render audit.** `crates/cli/src/command/run.rs:470`
  hardcodes cpal's `output_channels: 2`, and `LIVE_OUTPUT_CHANNELS = 2`
  feeds the live-path validator (`run.rs:275`). The live path silently
  rejects 3+ channel configs that the offline path already handles. A
  one-flag fix (`--output-channels`, validated against
  `MAX_OUTPUT_CHANNELS`) closes the drift before it ossifies into a
  surprise for live users.

End goal: `OfflinePcm` is interleaved + accessor-based; `agogo render
--wav-out FILE.wav` writes a multi-channel WAV that round-trips through
`hound` to bit-identical PCM; live `agogo run` honours
`--output-channels` up to the same `MAX_OUTPUT_CHANNELS=16` cap as the
offline path.

## Approach

One sprint, one branch (today's slot: `plan/2026-05-06-01`). Storage
refactor first (T1) so WAV (T2) can build on it; live audit (T3) is
independent and lands last so a regression there can't block T1/T2.

`OfflinePcm` becomes:

```rust
pub struct OfflinePcm {
    pub interleaved: Vec<f32>,   // length = frames * channels
    pub sample_rate: u32,
    pub frames: u64,
    pub channels: u16,
}

impl OfflinePcm {
    pub fn lane(&self, lane: u16) -> impl Iterator<Item = f32> + '_;
    pub fn into_planar(self) -> Vec<Vec<f32>>;
}
```

This is a public-API change to a struct merged on the previous PR.
There are exactly two in-tree consumers:
`crates/agogo/test/inter_channel_accuracy.rs` (39 `pcm.lanes[...]`
sites) and the new T2 WAV writer. Test sites migrate to a single
`let planar = pcm.into_planar();` at the top of each property —
keeps the body unchanged and amortises the transpose cost once per
case (still cheaper than 1.5M pushes during capture).

## Tasks

### T1 — Interleaved `OfflinePcm`

`crates/core/src/transport.rs`:
- Replace `OfflinePcm.lanes: Vec<Vec<f32>>` with
  `interleaved: Vec<f32>` + `channels: u16` (carrying the lane count
  so consumers can stride without re-passing the config).
- Replace `CapturedLanes = Vec<Vec<f32>>` type alias with
  `CapturedPcm = Vec<f32>` (single Vec, capacity `total_frames *
  channels`, pre-allocated once before the buffer loop).
- In `render_offline_with_rate`, replace the per-sample push loop
  (lines 963-971) with `captured.extend_from_slice(&output)` inside
  the existing `if let Some(captured) = captured.as_mut()` arm. The
  `// PCM ABI` comment migrates with the line.
- Add `OfflinePcm::lane(&self, lane: u16) -> impl Iterator<Item = f32> + '_`
  using `skip(lane).step_by(channels)` over the interleaved Vec.
  Out-of-range `lane` returns an empty iterator (the renderer
  validator already rejects out-of-range lanes upstream, so this is
  belt-and-braces, not user input).
- Add `OfflinePcm::into_planar(self) -> Vec<Vec<f32>>` for tests
  that need owned per-lane Vecs (one allocation per lane, then
  pre-sized `extend` from the strided iterator).
- Add `OfflinePcm::frame(&self, frame_idx: u64) -> &[f32]` returning
  the `channels`-wide slice for a given frame — used by the WAV
  writer in T2 and the spot-check that verifies interleaving order.
- The aggregate-stats loop (`for &sample_value in output.iter()`,
  lines 949-961) is unchanged — it already iterates the interleaved
  buffer.

`crates/core/src/lib.rs` and `crates/agogo/src/lib.rs`: no re-export
list change (still `OfflinePcm`); the struct's field set changes
under the same name.

`crates/agogo/test/inter_channel_accuracy.rs`:
- Add `let pcm = pcm.into_planar();` immediately after each
  `render_lanes_ok(...)` call site so existing `pcm[i][j]` indexing
  works unchanged. (Or: rebind `let lanes = pcm.into_planar();` and
  switch to `lanes[i][j]` — whichever reads cleaner per site.)
- `prop_buffer_boundary_invariance` (currently `&a.lanes == &b.lanes`
  per render): switch to `prop_assert_eq!(&a.interleaved,
  &b.interleaved)` to compare one Vec instead of N — the proptest
  case shrinks by one allocation per render.
- `prop_n_channel_independence`: keep planar comparison (per-lane
  isolation is the assertion); add `into_planar()` upfront on both
  the full and solo renders.

### T2 — `agogo render --wav-out FILE`

`crates/cli/Cargo.toml`:
- Add `hound = "3.5"` (workspace dev-deps already pin no-default-features
  for sibling crates; check `Cargo.toml` for the workspace pattern and
  match it).

`crates/cli/src/command/render.rs`:
- Add `pub wav_out: Option<String>` to `RenderArgs` with a `--wav-out
  FILE` argv flag. When `Some`, the renderer captures PCM and writes a
  WAV alongside the JSON report; when `None`, behaviour is unchanged
  (existing JSON-only callers are byte-identical).
- When `--wav-out` is set, switch from `render_offline` to
  `render_offline_capture`, then write a 32-bit float WAV via
  `hound::WavWriter` with header `(channels=output_channels,
  sample_rate=args.sr, bits_per_sample=32, sample_format=Float)`.
  Float-PCM WAV avoids the f32→i16 quantisation step and matches the
  renderer's native sample format.
- Stream the interleaved Vec directly into `WavWriter::write_sample`
  in one pass (`pcm.interleaved.iter().for_each(|&s|
  writer.write_sample(s))?`). No transposition.
- Path errors (parent dir doesn't exist, write permission denied) are
  converted to `String` errors at the boundary, matching the existing
  `render` handler's error style. No panics.
- The JSON report still prints; the WAV is a side-effect. Test that
  the JSON aggregates and the WAV's per-frame energy match.

`crates/cli/src/parse.rs`: add a path-string parser if needed
(probably just `String`-typed argv with validation in the handler).

## Deferred

- **Multi-tail-pending in `AudioClickState`**
  (`crates/chan/src/sink/audio.rs:180-192`). Only the most recently
  truncated click's tail resumes across a buffer boundary. Fine grids
  (`T256` / `T512P`) at high BPM where event spacing drops below
  `click_len` silently lose earlier overlapping tails. Proper fix: a
  bounded queue of pending tails plus decoupling state advancement
  from output writing so the unsplit-render order is preserved across
  the shared filter / RNG state. Out of scope here — distinct from
  PCM ABI work, lives in chan crate semantics. Track for a chan-only
  plan; until then `prop_buffer_boundary_invariance` deliberately
  doesn't exercise this regime.
- **`agogo render --wav-out` with i16 / i24 output formats.** This
  plan ships float-only WAV (lossless, matches renderer's native
  format). Integer formats need a documented dither / quantisation
  policy and are best landed alongside a peak-normalisation pass —
  separate plan.
- **Cpal device-capability probing in `agogo run`.** When the user
  requests N channels and the device only supports M, cpal's stream
  build fails with its own error string. A friendlier "your device
  supports up to M channels — try `--output-channels M`" message
  would need device enumeration on every run. Out of scope; the
  cpal error is already actionable.
- **Streaming WAV writer for very long renders.** Current path
  buffers the full interleaved Vec in memory before writing.
  Acceptable for any practical render (1 hour × 16ch × 48k × 4B =
  ~11 GB — already impractical for in-memory regardless). Streaming
  would pre-allocate the WAV header, write per-buffer, and finalise
  the data-chunk size at the end; revisit if hour-long renders
  become a workflow.

None. The storage shape (interleaved + accessors), the WAV format
